# ERLAB 設計メモ

最終更新: 2026-09-08

## 1. コンセプト

- 舞台は救急外来に隣接する臨床検査室。プレイヤーは臨床検査技師。
- **医師パートは作らない。** 病名・治療・薬・画像診断を持ち込むと医学データが爆発するため、検査室に特化する。
- プレイヤーは病名を当てなくてよい。判断するのは以下だけ。
  1. 数字のどこが異常か
  2. その異常は本物か（検体不良・前回値との乖離・矛盾）
  3. 再検・再採血が必要か
  4. どのレベルで報告するか（通常／至急／緊急）
- 「遊んでいたら検査値に強くなっていた」を狙う。ただし医学教育教材は名乗らない。

## 2. 世界観・リアリティの方針

### リアルに寄せる部分（公開資料で固める）
- 基準範囲、H/L/HH/LLフラグ
- パニック値（緊急異常値）の閾値
- 検体トラブルの影響
  - 溶血 → K・LD・AST 上昇
  - フィブリン析出・EDTA凝集 → 偽性血小板減少
  - 採血管間違い（EDTA混入でK↑Ca↓ など）
  - 検体量不足 → 測定不可・希釈
  - 点滴側採血 → 希釈・ブドウ糖↑
- 前回値との比較（デルタチェック）
- 報告フロー（通常＝結果送信／至急＝担当医へメッセージ／緊急＝電話＋読み返し確認）
- 装置ごとのTATの「比率」（血算 数分、生化学 30〜60分、血液ガス 即時、血液培養 日単位）

### 意図的に割り切る部分
- 基準範囲・パニック値は施設差がある → **「架空の病院の運用規定」として1セットに固定**し、出典をdocsに残す
- 時間は圧縮する（TATの比率は維持、絶対値は短縮）
- 「報告が遅れて急変」は演出。因果を強すぎにせず、経過は確率的に扱う
- トリアージ（患者を誰に診せるか）は看護師・医師の役割なので、検査技師にはやらせない。代わりに「報告レベルの選択」がその判断を担う

### 出典の扱い
- 基準範囲・パニック値・検体トラブルの影響量は `docs/sources.md` に出典（学会ガイドライン、検査会社の検査案内など）を記録する
- 将来、医師に「医者が見て笑うレベルの間違いがないか」だけ見てもらう可能性があるため、根拠は追える形で残す

## 3. 画面構成（3つだけ）

すべてテキストとテーブル。グラフィック素材は不要。実際の検査室がPC画面（LIS）を見て仕事をしている世界なので、PC画面を模すこと自体が再現になる。

### 3-1. LIS（検査情報システム）結果画面
- 表形式: 項目名 / 結果値 / 単位 / 基準範囲 / フラグ / **前回値**
- 異常の表示は**フラグ記号（H, L, HH, LL）が主**。色は補助として、そのフラグ欄のセルだけに付ける
  （H/L は淡い黄、HH/LL は淡い赤）。結果値・項目名・行全体・正常セルは塗らない。
  色は「ここに異常がある」という合図だけを担い、種類も重症度も色では伝えない。
  色を消しても記号と数値で同じ判断ができる状態を保つ
- 検体状態欄にコメントが入る（「溶血（+）」「フィブリン析出」「量不足」など）。見落とすと騙される。
  コメントがあるときだけ枠と地色で目立たせる（空欄のときは何もしない）
- 再採血を依頼すると、同じ画面の下に再採血検体の結果が並ぶ。前回値欄には最初の検体の値を入れて、
  どこが動いてどこが動かなかったかを見比べられるようにする（`recollect`）
- 項目名タップで索引（用語集）パネルが開く。パネルは「項目」「言葉」の二タブ。
  検体状態欄の語・フラグ記号・Δ・列見出しからは「言葉」（`data/glossary.json`）が開く
- 行をタップするとマーク（反転）が付き、その行だけが報告に載る。マーク0件でも報告できる。
  マークした行の下に疑いタブ（本物の異常／溶血／凝集／希釈・点滴側／取り違え／前回値との乖離）が開く。
  反転は選択状態の表示で、値の重さではない（詳細は `docs/mechanics.md`）

### 3-2. 装置モニタ／受付一覧
- 受付番号 / 患者ID / 依頼元 / 依頼項目 / 状態（受付・測定中・完了・再検）
- ER検体は「至急」マークで上に並ぶ
- 新人モードでは時間無制限なので、キュー管理・優先順位はまだゲーム性にしない（上級で解禁）

### 3-3. 院内メッセージ（グループウェア風）
- シフト開始時に「前シフトからの申し送り」が届く
  - 例: 「患者Bは輸血後なのでHbが動きます」「装置2は校正中で30分使えません」
- 新人モードの解説メールも同じ枡で出す（別UIを作らない）
- 医師からの返信もここに来る（「重症感染症を疑い治療開始」など、プレイヤーが後から学べる情報）
- ストーリー・フレーバーはここに乗せる

### 報告操作
| レベル | 操作 | 使い方 |
|---|---|---|
| 通常報告 | 結果送信ボタン | 電子カルテに結果を送る |
| 至急報告 | 担当医宛メッセージ | 担当医・ERへ直接連絡。コメントを付けられる |
| 緊急報告 | 電話画面 → 読み返し確認をタップ | パニック値。救急担当・上級医へ即時連絡 |

- 報告に添えるコメントは自由記述にしない。画面で選んだマーク・疑い・検体状態・再採血の結果から
  候補を組み、一〜三行タップで選ぶ（`data/comment_templates.json`）。選んだ行がそのまま文面になり、
  緊急報告の電話でも読み上げる
- 評価は「必要十分な判断で正解に到達したか」。全部緊急報告は減点（医師の信頼が落ちる）。パニック値を通常報告にすると患者経過が悪化しうる。

## 4. 新人研修モード（最初に作るもの）

- **時間無制限**
- 軽い患者から
- 索引（用語集）が常時開ける
- 横にナビが出て、異常値の意味と推奨される報告レベルを説明する
- 上級になるとナビと索引を外す。ここまで来ると成長＝上達になる

### 指導役

開始時に指導役を1人選ぶ（`data/mentors.json`）。ナビはその人の言葉だけで出る。

- **教える中身は変えない。変えるのは言い方だけ。** どちらを選んでも同じ判断にたどり着けること
- メッセージは `speaker` を持てる。`speaker` があるものはその指導役を選んでいるときだけ表示し、
  ないものは全員に出る（申し送り・医師からの返信は共通）
- 症例の `nav` や `handover` は、文字列でも配列でも書ける。配列にすると指導役ぶんを並べられる
- 切り替えは描画時に効く。途中で変えると、すでに出ている台詞ももう一方の言い方に差し替わる
- 現状は器と切り替えのみ。台詞は挨拶2本と症例1のナビ2本が仮で入っているだけで、
  症例2以降のナビはまだ指導役共通

### ナビの指さし
症例1〜3のナビは、文ごとに `focus`（画面の領域ID）を持てる。その文に付く「ここ」を押すと、
画面のその場所の枠が2秒だけ点いて消える。一文に一か所だけ。症例4以降には書かない。

### 索引の型（全項目この5枠で固定）
1. 何を測っているか
2. 基準範囲（この病院の規定）
3. 高いと何が考えられるか
4. 低いと何が考えられるか
5. 検体トラブルで偽の値が出る条件

### 段階設計（最初の6〜8症例）
1. 全項目正常。「異常なし・通常報告」を選ぶだけ。フラグの見方と送信操作を覚える
2. 1項目だけ軽度H（CRP 2.5 など）。通常報告でよいことを覚える
3. 中等度異常（Hb 9台の貧血）。急がないが「コメント付きで送る」判断
4. 初めてのパニック値（K 6.8、溶血なし）。緊急報告の手順（電話→読み返し）を覚える
5. 同じK 6.8、ただし溶血（3+）。素のKは4.6で、溶血の上乗せだけでパニック値に見えている。
   **「即報告が正解ではない」**を初めて体験。選択肢: ①そのまま即報告 ②溶血ありと付記して報告 ③再採血依頼。
   再採血すると基準範囲に戻る
5-b. 溶血（2+）でK 6.9。ただし素のKは6.0で、腎機能低下（Cre 3.2、前回K 5.8）がある。
   再採血しても6.0が残り、パニック値のまま。**「溶血があっても本物のことがある」**。
   5の直後に続けて出す。検体を疑うことと、異常を否定することは別だと分けさせる
6. 前回値との乖離（Hb 13.5 → 9.8）。デルタチェック、再検、患者確認

ここまでで検査室の判断の型がほぼ出揃う。以降は型の組み合わせと項目の入れ替え。

## 5. データ設計

### ファイル分離（すべてJSON）
- `data/tests.json` — 検査項目（名称、単位、基準範囲、パニック値、索引5枠、桁数）
- `data/conditions.json` — 病態テンプレート（根っこの値の範囲と関係性）
- `data/artifacts.json` — 検体トラブル（種類、影響する項目と加算・乗算ルール、検体コメント文）
- `data/hospital.json` — 架空病院の運用規定（基準範囲セット、パニック値、報告ルール、TAT）
- `data/cases/*.json` — 症例（新人モードは手書きで固定。生成器はその後）
- `data/messages/*.json` — 申し送り・解説・医師返信の文面
- `data/suspects.json` — マーク行に付ける疑い（検体・検査室側の見立てのみ。病名は入れない）
- `data/glossary.json` — 画面に出る言葉の辞典（16語・一語三行）と「見る順番」の五行
- `data/comment_templates.json` — 報告に添えるコメントの候補の型

### 数値のリアリティ確保：根っこの値だけ生成し、派生値は計算する
手作業で全項目を書くと必ず矛盾する。計算で担保する。
- RBC・MCV・MCH を決める → Hb・Ht を導出（Ht = RBC × MCV、Hb = RBC × MCH）
- Na・Cl・HCO3 を決める → アニオンギャップを導出
- 溶血フラグ → K・LD・AST に規定量を加算
- 希釈フラグ → 全項目を一定比率で下げ、Gluのみ上げる
- 派生ルールは `src/derive.js` に集約し、テストを書く

### 症例の構造
```json
{
  "id": "n01",
  "mode": "rookie",
  "patient": { "id": "P-0001", "age": 34, "sex": "F", "from": "ER" },
  "handover": "msg_n01_intro",
  "order": ["CBC", "CHEM_BASIC"],
  "seed": { "condition": "normal", "severity": 0 },
  "artifact": null,
  "previous": null,
  "nav": "msg_n01_nav",
  "choices": [
    { "when": { "recheck": true }, "score": "poor", "headline": "再検の理由がありません", "reply": "msg_n01_recheck" },
    { "when": { "report": "routine" }, "score": "best", "headline": "適切な報告です", "reply": "msg_n01_ok" },
    { "when": {}, "score": "poor", "headline": "過剰報告です", "reply": "msg_n01_over" }
  ]
}
```

### 判定は「単一の正解」ではなく選択肢ごとの評価

検査室の判断には、○×では表せない場面がある。溶血検体のKを「そのまま即報告」
「溶血ありと付記して報告」「再採血を依頼」で比べると、正解はひとつではなく、
**最善・許容・要改善**の3段階になる。だから症例は正解をひとつ持たず、`choices` に
選択肢ごとの評価と医師返信を並べる。

- `when` … その枝に当たる条件。書いた項目だけを見る（書かない項目は不問）
  - `report` 報告レベル（`routine` / `urgent` / `emergency`）
  - `recheck` 再検・再採血を依頼したか
  - `comment` コメントを書いたか（真偽値。中身は見ない）
  - `readback` 読み返し確認をとったか
  - `marks` マークした項目（`must` / `max` / `forbid`）
  - `suspects` マーク行に付けた疑い（項目ごとに配列。`exact: true` で厳密一致）
  - `comment` コメント（`true`／`false` は一行以上あるか。配列で書くと候補IDの指定になる）
- `score` … `best` 最善 / `ok` 許容 / `poor` 要改善
- `headline` … 判定画面の見出し
- `reply` … 院内メッセージに流す文面のID

上から順に見て、最初に当たった枝を採用する。特殊な条件を上に、一般的な条件を下に置く。
**最後の枝は `when` を空にして受け皿にする**（どの操作でも必ず判定と返信が返るように）。
この形は `test/report.test.js` で検査している。

### 二段の症例（医師の差し戻し）

医師の返信が差し戻しで返り、二本目を報告し直す症例がある（症例7。仕様は `docs/case07.md`）。
枝に次の三つを足す。**どれも書かなければ、いままでの症例はそのまま動く。**

- `then: "followup"` … この枝では症例を閉じない。`doctor` だけ届けて `followup` に進む
- `cap` … 最終評価の上限（`best` / `ok` / `poor`。既定は `best`）。一本目の甘さぶん、
  二本目で挽回しきれないようにする
- `followup` … `handover`（差し戻し後の指導役の一言）、`recollect`（二本目の上書き値）、
  `choices`（二本目の判定）

**最終評価は min（二本目で当たった枝の `score`、一本目の `cap`）。** `followup` の枝に
`then` は書けない（入れ子にしない）。

## 6. 技術方針

- 単一HTML（index.html）＋ `src/*.js` ＋ `data/*.json`。開発中は素のES modulesでよい。PLiCyに出すときは1ファイルに結合
- 依存ライブラリなし、または最小
- セーブはlocalStorage（PLiCy上では使用可）
- スマホ縦画面でも表が崩れないこと（PLiCyはスマホ利用が多い）
- フォントは等幅を基本にし、LISっぽさを出す

## 7. 最初のマイルストーン

1. `data/tests.json` に血算・生化学の基本20項目（索引5枠込み）
2. `src/derive.js` に派生値計算＋溶血・希釈の加算ルール＋テスト
3. `data/hospital.json` に基準範囲・パニック値1セット（出典は `docs/sources.md`）
4. 新人モードの症例1〜3をJSONで手書き
5. LIS画面・院内メッセージ画面・報告ダイアログを持つ index.html
6. 画面で見て「検査室っぽいか」を確認 → 方向修正 → 症例4〜6

## 8. やらないこと（非目標）

- 医師視点のプレイ、病名確定、治療選択
- 疾患500種類のデータベース
- 画像検査（CT/MRI/X線）
- リアルタイムの時間制限（新人モードでは）
- 実在施設の基準値の再現
